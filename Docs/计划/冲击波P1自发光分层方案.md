## 0. 结论先行

放弃「挂真实灯光」方案，回归**模型自身自发光**，但把当前「一整片涂抹的发光层」拆成**三层结构**：

| 层  | 名字      | 作用             | 亮度                           | 面积             |
| -- | ------- | -------------- | ---------------------------- | -------------- |
| L0 | 主体 Body | 能量体本身（渐变 + 色相） | 中等，**不超过 1**                 | 整个 mesh        |
| L1 | 内芯 Core | 前沿 / 拱顶的高温亮线   | **很亮（1.5~2.5）**，刚好过 Bloom 阈值 | **很窄（10~20%）** |
| L2 | 外壳 Halo | 溢出到模型轮廓外的柔光    | **很淡（0.15~0.4）**，低于 Bloom 阈值 | **很宽（沿法线外扩）**  |

**层次的本质 = 亮度与面积成反比**：越亮越窄、越淡越宽。这正是当前实现缺失的东西。

---

## 1. 当前 P1 的三个问题（诊断）

当前实现是 shader 末尾一个 Additive Pass：  
`mask = (pow(vy, _GlowArch) * 0.75 + pow(t, _GlowFront)) * tail + _Flash * 0.8`

| # | 问题            | 根因                                                                            |
| - | ------------- | ----------------------------------------------------------------------------- |
| ① | **光晕出不了模型轮廓** | Additive 只在 mesh 覆盖的像素上叠加。Bloom 虽会向外模糊，但散射半径有限，溢出感很弱 → 光像"贴在表面的贴纸"，不像"从里面发出来" |
| ② | **没层次**       | `crest*0.75 + front` 覆盖整个拱顶 + 整个前沿，是一片**均匀亮区**，没有"亮芯 → 外晕"的过渡带                |
| ③ | **不是过曝就是没变化** | 只有"整体强度"一个旋钮。调低 → 整片一起变暗（感觉没变化）；调高 → 整片一起过 1（过曝）。**缺少"面积"与"强度"的分离控制**         |

---

## 2. 为什么放弃灯光方案（用户判断，已确认）

| 顾虑        | 说明                                                                             |
| --------- | ------------------------------------------------------------------------------ |
| **性能**    | URP Additional Lights 在移动端有 per-pixel 开销，且要关阴影才划算，关了阴影又失去大部分意义                 |
| **形状不吻合** | 冲击波是**长条 + 拱形**（沿 Z 铺满场地、沿 X 推进、Y 拱起）。点光源是**球形衰减**，无论怎么摆都无法贴合长条轮廓，光斑会溢出到不该亮的区域 |

**关键替代洞察**：既然要"光溢出模型轮廓"，那就**让模型自己膨胀一圈**来产生光晕 —— 形状 100% 吻合，且不需要任何光照计算。

---

## 3. 核心手段：外壳膨胀光晕（Shell Halo）

在 shader 里加一个 Pass，把顶点**沿法线向外推** `_HaloWidth`，用 Additive + 软衰减渲染。

```hlsl
float3 pos = IN.positionOS + IN.normalOS * _HaloWidth;
```

为什么这个方法能同时解决三个问题：

| 问题       | 解法                                       |
| -------- | ---------------------------------------- |
| ① 光溢出轮廓  | 外壳在轮廓之外渲染 → 光晕**物理上**位于模型外面，视觉上就是"光溢出来了" |
| ② 没层次    | 内芯（窄亮）+ 外壳（宽淡）形成**两段式过渡**，中间自然出现层次       |
| ③ 过曝/没变化 | 内芯管**面积**（收窄）、外壳管**外溢**，强度各自独立 → 两个旋钮解耦  |

代价与收益：

- 开销 = 一个额外 Pass（顶点外扩 + 简单 frag），**不引入 Additional Light、不吃光照计算**
- 形状 = 模型自身的膨胀 → 长条拱形完美吻合

---

## 4. 三层详细设计

### L1 内芯 Core（改造现有 Glow Pass）

把现有发光层**收窄、提亮、向白偏移**：

- `pow` 指数调大 → 亮区面积收缩到前沿 / 拱顶的一小条
- 强度调低（因为收窄后单位面积亮度已经够，不需要靠高强度堆视觉冲击）
- 引入 `_CoreWhiteness`：内芯向白色偏移，形成"高温核心发白"的观感

```hlsl
// 内芯：窄而亮，向白偏移
float crest = pow(IN.vy, _GlowArch);     // 指数大 => 只拱顶一小条
float front = pow(IN.t,  _GlowFront);    // 指数大 => 只前沿一小条
float mask  = saturate(crest * 0.6 + front) * tail;

half3 core = _GlowColor.rgb;
core = lerp(core, half3(1,1,1), _CoreWhiteness * mask);   // 越亮处越白
half3 g = core * _GlowIntensity * mask + _Flash * 0.8;
```

### L2 外壳 Halo（新增 Pass）

沿法线外扩 + 宽而淡的 mask：

```hlsl
struct AttributesHalo
{
    float3 positionOS : POSITION;
    float3 normalOS   : NORMAL;   // 需要法线，用于外扩
};

VaryingsHalo vertHalo(AttributesHalo IN)
{
    VaryingsHalo o;
    float3 pos = IN.positionOS + IN.normalOS * _HaloWidth;   // 沿法线外扩
    o.positionHCS = TransformObjectToHClip(pos);
    // t / vy 仍按【原始】 positionOS 计算，保证与主体同一套渐变坐标
    float span = max(0.0001, abs(_FrontX - _BackX));
    o.t  = clamp((IN.positionOS.x - _BackX) / span, 0.0, 1.0);
    o.vy = clamp(IN.positionOS.y / max(0.0001, _ArchHeight), 0.0, 1.0);
    return o;
}

half4 fragHalo(VaryingsHalo IN) : SV_Target
{
    if (_HaloIntensity <= 0.001) discard;

    float tail  = smoothstep(_HaloTailCut, min(1.0, _HaloTailCut + 0.35), IN.t);
    float crest = pow(IN.vy, _HaloArch);     // 指数小 => 比内芯宽
    float front = pow(IN.t,  _HaloFront);
    float mask  = saturate(crest * 0.8 + front) * tail;
    mask = pow(mask, _HaloSoftness);         // 外缘软化，避免硬边

    return half4(_GlowColor.rgb * _HaloIntensity * mask, 1.0);
}
```

Pass 状态：`Blend One One`、`ZWrite Off`、`ZTest LEqual`、`Cull Off`、`LightMode = UniversalForward`。

> **坐标空间铁律**（血泪教训）：`t / vy` 必须用 **`positionOS`** 推导，与主体 Pass 严格一致。>   
> 之前把 shader 改成世界坐标、而 `SyncMaterial` 仍用 `importedMesh.bounds` 覆盖 `_BackX/_FrontX`，>   
> 两套坐标冲突导致 `t` 恒为 0、alpha 恒为 0，冲击波**完全看不见**。改 shader 时绝不碰坐标空间。

## 6. 调参原则（防过曝，务必按顺序）

1. **先调面积、再调强度**：先把 `_GlowArch` / `_GlowFront` 调大把内芯收窄，再定 `_GlowIntensity`。
2. **内芯亮度 1.5~2.5**：刚好越过 Bloom 阈值，让 Bloom 只负责柔化这一小条。
3. **外壳亮度 0.15~0.4**：刻意压在 Bloom 阈值之下 —— 它的职责是"柔光包裹"，不是"发光"。
4. **Bloom intensity 降到 0.5~0.6**：外壳已经提供了光晕，Bloom 不必再强行拉高（当前 0.85 偏高，是过曝帮凶）。
5. **验收标准**：远看有光晕包裹、近看有亮芯、两者之间有过渡 → 层次成立。     
   若"整片一起亮" = 内芯没收窄；若"完全没光感" = 外壳太淡或 `_HaloWidth` 太小。

| **WALL.fbx 法线异常** | 外壳沿法线外扩时裂开 / 翻面 | fallback：改用「绕 mesh bounds 中心缩放膨胀」，`pos = center + (pos - center) * scale`，由 C# 传 `_MeshCenter`。先验证法线再决定 |

### 11.0 前置事实核对（本文档旧内容与工程现状不一致处，已更正）

| 项               | 文档旧值     | **工程实际值**                       | 影响                                              |
| --------------- | -------- | ------------------------------- | ----------------------------------------------- |
| Bloom intensity | 0.85（偏高） | **0.4**                         | 已经不高，不必降；反而可能要**略升**                            |
| Bloom threshold | —        | **0.8**                         | 内芯亮度必须 > 0.8 才会泛光                               |
| Bloom scatter   | —        | 0.6                             | —                                               |
| Glow Pass 顶点属性  | 未说明      | **只有 POSITION，没有 NORMAL**       | 法线外扩 / fresnel 都需先补 NORMAL                      |
| Glow Pass Cull  | 未说明      | **Cull Off**                    | 正反面各画一次 → **实际亮度 = 2 × \_GlowIntensity**，是隐性过曝源 |

> ⚠ 结论：Bloom 不是问题，**当前过曝的主因是 Cull Off 的双面叠加 + 内芯面积太大**。Step A 就能解决大半。

### 11.1 Step 0：先定 Halo 的外扩方式（必须先拍板，三条路径）

外壳光晕的核心是"把 mesh 变大一圈再画一遍"。变大的方式有三条路：

| 路径               | 做法                                   | 优点                                 | 缺点                        | 依赖                      |
| ---------------- | ------------------------------------ | ---------------------------------- | ------------------------- | ----------------------- |
| **A 法线外扩**       | `pos + normalOS * w`                 | 形状 100% 贴合；能做 fresnel（轮廓处最亮，最像真光晕） | 硬边 / 接缝处法线不连续 → **壳体裂开**  | **需要 NORMAL**，且法线质量要好   |
| **B 分量缩放膨胀** ⭐推荐 | `pos + (pos - center) * (0, sy, sz)` | 不依赖法线、绝不裂开；**X 不膨胀**，中缝位置不穿帮       | 没有 fresnel，边缘柔度靠 mask 软化  | 仅需 C# 传 `bounds.center` |
| **C 双层壳**        | A/B 各画两层（0.05 淡 + 0.15 更淡）           | 形成两级亮度台阶，最像渐变                      | 两个 Pass，移动端多一次全屏 overdraw | 同 A 或 B                 |

**为什么推荐 B（且 X 不膨胀）**：冲击波是「沿 Z 铺满场地 / 沿 Y 拱起 / 沿 X 推进」的长条。  
X 方向膨胀会让光晕越过中缝盖到对手区域 —— **中缝位置是玩法信息，不能被光晕糊掉**。  
只膨胀 Y（拱顶变高）与 Z（前后变宽）正好对应"光从墙上/前后溢出来"，视觉正确且不影响判定可读性。

**Step 0 的唯一动作：验证 WALL.fbx 法线**（决定要不要走 A 的 fresnel）

1. Project 选中 `Assets/Art/VFX/WALL.fbx` → Inspector → **Model** 页最下方看顶点数；
2. 切到 **Skinned Mesh / Mesh** 预览，或在 MeshFilter 上用 `Debug` 模式看 `normals` 数组是否非空；
3. 最快：在场景里选中墙，临时把 shader 的 Glow Pass 改成输出 `normalOS` 当颜色，看是否出现**平滑的彩色渐变**（裂开 = 法线不连续 → 走 B）。

| 动作            | 参数                                     | 现值 → 建议                         |

### 11.3 Step B：新增 Halo Pass（按 Step 0 结论二选一）

#### B-方案（分量缩放膨胀，零法线依赖）

```hlsl
// Properties 新增
_HaloIntensity ("Halo Intensity", Float) = 0.35
_HaloExpand    ("Halo Expand (xyz)", Vector) = (0, 0.12, 0.12)  // ⛔ X 必须为 0
_HaloCenter    ("Halo Center OS", Vector) = (0, 0, 0)           // C# 传 importedMesh.bounds.center
_HaloArch      ("Halo Arch Focus", Float) = 1.5                 // 比内芯小 => 比内芯宽
_HaloFront     ("Halo Front Focus", Float) = 1.2
_HaloTailCut   ("Halo Tail Cut", Range(0,1)) = 0.1
_HaloSoftness  ("Halo Softness", Float) = 1.8

VaryingsHalo vertHalo(AttributesHalo IN)
{
    VaryingsHalo o;
    float3 off = (IN.positionOS - _HaloCenter) * _HaloExpand.xyz;
    o.positionHCS = TransformObjectToHClip(IN.positionOS + off);
    // ⛔ 铁律：t / vy 用【原始】positionOS，与主体 Pass 严格一致
    float span = max(0.0001, abs(_FrontX - _BackX));
    o.t  = clamp((IN.positionOS.x - _BackX) / span, 0.0, 1.0);
    o.vy = clamp(IN.positionOS.y / max(0.0001, _ArchHeight), 0.0, 1.0);
    return o;
}

half4 fragHalo(VaryingsHalo IN) : SV_Target
{
    if (_HaloIntensity <= 0.001) discard;
    float tail  = smoothstep(_HaloTailCut, min(1.0, _HaloTailCut + 0.35), IN.t);
    float crest = pow(IN.vy, max(0.01, _HaloArch));
    float front = pow(IN.t,  max(0.01, _HaloFront));
    float mask  = saturate(crest * 0.8 + front) * tail;
    mask = pow(mask, _HaloSoftness);            // 外缘软化，避免硬边
    return half4(_GlowColor.rgb * _HaloIntensity * mask, 1.0);
}
```

Pass 状态：`Blend One One`、`ZWrite Off`、`ZTest LEqual`、**`Cull Back`**（避免双面翻倍）。


#### A-方案（法线外扩 + fresnel，法线可用时效果更好）

```hlsl
float3 pos = IN.positionOS + IN.normalOS * _HaloWidth;
...
// fresnel：掠射角（轮廓边缘）最亮，正对相机最淡 —— 这才是"光晕"的形状
half fres = pow(1.0 - abs(dot(normalize(IN.normalWS), normalize(IN.viewDirWS))), _HaloFresnel);
mask *= fres;
```

| 对比   | A            | B                    |
| ---- | ------------ | -------------------- |
| 轮廓吻合 | 100%         | 90%（等比膨胀，长条两端会略微外扩）  |
| 边缘柔度 | fresnel 天然柔和 | 靠 `_HaloSoftness` 硬调 |
| 裂开风险 | 有            | **无**                |

### 13.2 实测失败现象（用户验收）

1. **中缝被撑得巨大、无法闭合** —— 破坏了此前已验收的冲击波主体表现，属不可接受。
2. **完全没有光感** —— 点击「打印 Halo 平滑法线统计」后画面无任何可见变化。

### 13.3 根因分析

#### ① 中缝撑大：把运行时 Mesh 赋给了场景对象的 `sharedMesh`（主因，高危）

```csharp
_haloMesh = Instantiate(src);
_haloMesh.hideFlags = HideFlags.HideAndDontSave;   // 运行时临时对象，不可序列化
...
if (mf0 != null && mf0.sharedMesh != target) mf0.sharedMesh = target;   // ⛔ 写入场景对象
```

`ShockwaveMeshGenerator` 带 `[ExecuteAlways]`，`OnValidate/Refresh` 在 **Editor 非播放模式**也会执行。  
给场景对象的 `MeshFilter.sharedMesh` 赋一个 `HideAndDontSave` 的运行时 Mesh：

1. 场景立刻被标记为 dirty；
2. Unity 保存场景时**无法序列化该引用**，写出 `m_Mesh: {fileID: 0}`；
3. 墙的 mesh 引用丢失 → 墙体不渲染 → 中间只剩空隙。

这正是「缝变得好大、无法闭合」的成因 —— 不是光晕溢出，而是**墙本身没了**。  
（旁证：`BlueWall` 的 `MeshFilter` 在 YAML 里 `m_Mesh` 为 0；运行时靠 `Refresh()` 每帧重新赋 `importedMesh` 才显示，一旦保存场景就会穿帮。）

**⛔ 铁律补充：任何 `Instantiate` 出来的运行时 Mesh/Asset，绝不可赋给场景对象的 `sharedMesh` / `sharedMaterial`。**  
需要"带法线的 mesh 变体"时，只能在**运行时**（`Application.isPlaying`）替换，或用 `MeshFilter.mesh`（自动实例化副本）而非 `sharedMesh`。

#### ② 零光感：外扩量与亮度同时远低于可见阈值（量化）

| 量               | 值             | 问题                                                                         |
| --------------- | ------------- | -------------------------------------------------------------------------- |
| `haloWidth`     | 0.08 **世界单位** | 墙长约 6、高约 1.2 → 光晕宽度仅占墙长 **1.3%**，俯视锁视角下只有几个像素                              |
| Fresnel 指数      | 2.5           | 只有**极窄的掠射边缘**亮，而边缘宽度就是那 0.08 → 可见面积趋近 0                                    |
| `haloIntensity` | 1.0           | `_GlowColor`（1.0, 0.55, 0.62）亮度 ≈ 0.75 < **Bloom threshold 0.8** → 根本不触发泛光 |

**几何外扩 + Fresnel 双重收窄，再叠加不过 Bloom 阈值 = 画面上完全为零。** 这是参数设计错误，不是实现 bug。

#### ③ 附带教训

- `haloExpandX=0` 只能屏蔽**局部空间**的 X 分量；把外扩放到世界空间做，会受墙的巨大非均匀缩放（`localScale.x ≈ 157`）影响分量重分布，方向不再可控。
- FBX 的 `isReadable` 改动会让整份顶点数据常驻内存，冲击波这种大范围 mesh 不划算。

## 14. 替代方案（待拍板 · 未执行）：不碰几何的"指数分层"

核心思路：**"宽而淡"不需要靠几何外扩，靠【指数的大小】就能实现。**

同一个 `GlowAdditive` Pass 内把 mask 拆成两项相加（零几何风险、零中缝风险、零新 Pass）：

```hlsl
// 内芯：指数大 -> 范围窄、集中（现状 glowArch=10 / glowFront=6）
float core = pow(vy, _GlowArch) * 0.75 + pow(t, _GlowFront);

// 外壳：指数小 -> 范围宽、平缓（新增，宽而淡）
float halo = pow(vy, _HaloArchSoft) * 0.5 + pow(t, _HaloFrontSoft);

mask = (core * _GlowIntensity + halo * _HaloSoftIntensity) * tail;
```

| 参数                   | 建议起点     | 作用                  |
| -------------------- | -------- | ------------------- |
| `_HaloArchSoft`      | 1.5      | 拱向软光晕聚拢指数（**越小越宽**） |
| `_HaloFrontSoft`     | 1.2      | 前沿软光晕聚拢指数（越小越宽）     |
| `_HaloSoftIntensity` | 0.35~0.5 | 软层强度，必须显著低于内芯       |

优点：

- 完全在**原 mesh 轮廓内**绘制，中缝物理上不可能被撑大
- 不需要 mesh 副本、不需要法线、不需要改 FBX 导入设置
- 参数全部 Inspector 可调，`_HaloSoftIntensity = 0` 即关闭

缺点（需接受）：

- 光晕**不会溢出墙的轮廓外** —— 视觉上是"墙自身在发亮"，而不是"光从墙边溢出来"
- 想要真正的"溢出一圈"，只能靠 Bloom（把 `_GlowColor` 亮度提到 > 0.8 触发）

### 需要拍板

1. 是否接受「光晕不溢出轮廓」这个限制？（若能接受，就走指数分层）
2. 若必须溢出轮廓 —— 那唯一安全的做法是**给墙加一个独立的子物体 Halo 板**（自己的 Transform、自己的 mesh，不参与 `ShockwavePreview` 的缩放争夺），代价是多一个物体要同步位置/倍率。
3. `_GlowColor` 是否允许提亮到能过 Bloom 阈值（会改变现有色调）？

## 15. 两个新问题诊断（2026-10-07 截图 · 只诊断，未执行）

用户反馈两条，与"自身发亮"无关：

1. **与场景件的互动明显有问题（被遮挡）** —— 植物、树桩画在墙前面，墙像半透明玻璃被穿透。
2. **与场景的互动也毫无光感** —— 墙既不照亮自身轮廓，也不影响周围环境。

### 15.1 问题 ①：被遮挡的真凶是「UI Image」，不是 sortingOrder

**排查过程**：

| 检查项                   | 结果                                                                                      |
| --------------------- | --------------------------------------------------------------------------------------- |
| 墙的 `sortingOrder`     | **20，已是全场最高**（其余全为 0）                                                                   |
| 墙的 `sortingLayerID`   | 0（`Default`）                                                                            |
| 场景里有 SpriteRenderer 吗 | **0 个**                                                                                 |
| 植被是什么                 | 2 个 `Decoration`（**Image UI 组件** + CanvasRenderer）、2 个 `New Spine GameObject`（Spine 网格） |
| `Decoration` 的父级      | `HPBarLeft` / `HPBarRight` → 根级 **`HPBarCanvas`**                                       |
| `HPBarCanvas` 渲染模式    | **`ScreenSpaceOverlay`，sortingOrder = 100**                                             |

**结论**：`sortingOrder` 只在**同一渲染队列内部**排序。墙是 `MeshRenderer`（透明队列 3000），  
而 `Decoration` 是 **UI Image**（`CanvasRenderer`，Overlay 模式在**所有 3D 之后**绘制）。  
两者根本不在同一个排序体系里 —— **把墙的 sortingOrder 调到 999 也永远压不住 Overlay UI**。

⛔ 这就是"墙被植物穿透"的全部原因，**与墙本身、也与发光无关**。

### 15.2 问题 ②：毫无光感有三个叠加原因

#### 原因 A：内芯 glowIntensity 只有 0.9，叠加后过不了 Bloom 阈值

场景实测值（两堵墙一致）：

| 参数              | 当前值                  | 影响                        |
| --------------- | -------------------- | ------------------------- |
| `glowIntensity` | **0.9**              | 低于 1.0，Additive 叠加后峰值难超 1 |
| `glowColor` 红   | `(0.76, 0.40, 0.24)` | 亮度 ≈ 0.45                 |
| `glowColor` 蓝   | `(0.28, 0.47, 0.65)` | 亮度 ≈ 0.44                 |
| Bloom threshold | 0.8                  | 需要**最终帧缓冲亮度 > 0.8** 才泛光   |

峰值估算：`0.45 × 0.9 = 0.40` → **远低于 0.8，泛光量≈0**。  
即使把 `glowIntensity` 提到 1.6，峰值也才 0.72，**仍然不过阈值**。  
且 `glowArch=10 / glowFront=6`（你亲自调定的）把发光压得极窄，实际覆盖面积很小。

#### 原因 B：墙的 transform 缩放极端，导致世界空间尺度很怪

```
RedWall  localScale = (156.84, 4.08, 80.50)     ← X 是 157 倍！
BlueWall localScale = (-156.84, 4.08, 80.50)    ← 负号 = 镜像
```

这个 157 倍的 X 缩放是历史 `autoFit` 留下的（现已关闭、但 Transform 已被污染）。  
它让"世界单位"和"局部单位"差 157 倍，**任何按世界单位设计的参数（外扩宽度、软光晕宽度）  
在这个比例下都会失真** —— 这也是上一轮 A 路径量级算不准的深层原因。

#### 原因 C：Bloom 是全局后处理，UI 不参与

URP 后处理只作用于**相机渲染目标**。UI（Overlay）虽然在同一帧，但  
`SampleSceneProfile` 的 Bloom 只采样 3D 渲染结果，**不会给 UI 泛起光晕**。  
所以即便墙亮了，植物/树桩这些 UI 元素也不会被"照亮"。

### 15.3 方向讨论（三个待定方向 · 均未执行）

#### 方向 1：修遮挡 —— 必须动 UI 侧，不动墙

| 做法                                                           | 说明                                    | 风险                     |
| ------------------------------------------------------------ | ------------------------------------- | ---------------------- |
| **1-A 把 `Decoration` 从 Overlay Canvas 挪到 WorldSpace Canvas** | 让它进入 3D 透明队列，`sortingOrder` 就能压过/被压过墙 | 中：会改场景层级，位置要重新对        |
| **1-B 把墙也改成 UI 元素**                                          | 彻底统一到 UI 体系                           | 高：墙要跟随 3D 中缝移动，UI 化代价大 |
| **1-C 给 Overlay UI 加"洞"**                                    | 让墙所在区域不画 UI                           | 高：等于遮罩，逻辑脆弱            |

**我推荐 1-A**：把装饰层单独挂一个 `WorldSpace` Canvas，让它和墙在同一个透明队列里，  
再用 `sortingOrder` 明确谁先谁后。**这完全不动墙的代码。**

#### 方向 2：让墙自身有光感 —— 纯参数，零结构风险

在不动任何结构的前提下，先把内芯推到能泛光的量级：

| 参数                | 当前  | 建议起步           | 依据                            |
| ----------------- | --- | -------------- | ----------------------------- |
| `glowIntensity`   | 0.9 | **2.2 ~ 3.0**  | `0.45 × 2.5 ≈ 1.1` 才稳过 0.8 阈值 |
| `glowColor`       | 各自  | 亮度提到 **≥0.75** | 提高过阈值的余量                      |
| Bloom `intensity` | 0.4 | 0.6 ~ 0.8      | 泛光扩散更明显（全局生效，影响所有物体）          |
| Bloom `threshold` | 0.8 | **0.75 ~ 0.8** | 略降让泛光更容易触发                    |

⚠️ 这会**同时让场景里其他亮部也泛光**，需要你确认可接受。

#### 方向 3：让墙"照亮周围" —— 需要额外手段

Bloom 只能让**墙自己**发亮糊一圈，**不会把光洒到植物上**。若要"光溢出照亮环境"：

| 做法                                             | 说明                | 风险 |
| ---------------------------------------------- | ----------------- | -- |
| 3-A 加一个半透明的"光晕地板"（贴地 quad，Additive）            | 便宜，但形状是椭圆不是拱形，贴不准 | 中  |
| 3-B 用 URP 的 `Light Layer` + 一盏跟随墙的假 lightshaft | 移动端成本高（你已否决过真实灯光） | 高  |
| 3-C 放弃"照亮环境"，只做"墙自身轮廓发光 + 地面倒影"                | 卡通风格常见做法，成本最低     | 低  |

**我推荐 3-C 或 3-A 起步**：先确认"墙自身轮廓够亮"是否已经满足你的期望。
