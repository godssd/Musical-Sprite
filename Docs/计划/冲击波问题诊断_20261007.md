# 冲击波问题诊断报告（2026-10-07 录屏 QQ2026107-11178）

## 1. 验证到的异常现象

我已把录屏抽帧并生成接触表（见 `C:/Users/Administrator/Downloads/_frames/`）。从 20-30 秒、32-42 秒等高频段可以清晰看到：

1. **红蓝两条冲击波频繁"忽大忽小"**，粗状态往往只持续 0.2-0.6 秒就缩回。
2. **达到分差阈值后（看上方分数/血条已明显拉开）**，墙并没有稳定地保持粗状态，而是脉冲式抖动。
3. **偶尔会"切出"一次明显变粗，但立刻缩回**，像被弹了一下。
4. **两侧线不是平滑外扩，而是伴随明显开合动作**——这提示"大小"变化里混进了大量位置偏移。

## 2. 根因定位（按影响程度排序）

### 2.1 最大元凶：对峙呼吸参数被场景 YAML 覆盖成异常值

代码里的默认值：
```csharp
public float breathGapAmplitude = 0.12f;
public float breathPeriod = 2.4f;
```

但当前 `Assets/Scenes/SampleScene.unity` 里实际序列化值：
```yaml
breathGapAmplitude: 0.8      // 默认 0.12 的 6.7 倍
breathPeriod: 1              // 默认 2.4 的 2.4 倍快
```

这导致：
- 缝隙在 `centerGap=0.2` 与 `0.2+0.8=1.0` 之间快速摆动，**视觉上就是把墙"撑开/收回"**。
- 周期只有 1 秒，与战斗节奏同频，于是墙看起来在"不停大小变化"。
- 振幅 0.8 已经盖过了正常的缩放倍率变化（1.0→1.5 只是 50% 缩放，而呼吸开合直接把缝隙放大了 5 倍）。

结论：**用户看到的"大小频繁切"，很大一部分不是缩放，而是呼吸开合在抢戏。**

### 2.2 衰退中途重新前进会"先缩一下"

`UpdateDecay` 每帧都在降低 `scale` 和 `accum`：
```csharp
scale = ScaleFromProgress(p);
accum = decayStartAccum * (p / Mathf.Max(1e-5f, decayStartProgress));
```

如果在衰退进行了 0.5 秒后重新进入 Advancing：
- 当前 `scale` 可能还是 1.35（原本 1.5）。
- 但 `accum` 已经跟着衰退降到约 0.3 → `LookupScale(0.3)=1.1`。
- `GetAdvanceTarget` 返回 **1.1 < 1.35**，弹簧会把墙先压回 1.1，再重新往上爬。

这就出现了"刚变大又立刻缩回去"的脉冲。

用户原话是："衰退期进入前进停止衰减、维持当前大小、以当前累积为起点继续累积"。当前实现违背了这个"维持当前大小"——它允许 target 低于当前 scale。

### 2.3 Idle→Advancing 起跑仍有 8% 回缩蓄力

`forwardAnticipationScaleRatio=0.92` + 场景中 `forwardAnticipationTime=0.5`（比代码默认 0.18 更长）：

每次从 Idle 开始前进（高频对局中会出现反复 Idle→Advancing→Decay→Idle），墙会先被压到当前倍率的 0.92 倍，持续 0.5 秒。对于 1.0 倍来说就是先缩到 0.92，再涨。高频起跑时这就是"起步一抖一抖"。

### 2.4 阈值后"不怎么变大"是机制与倍率表不匹配

- `BattleCenterLine.pushPerHit = 0.001`，分差 3000 时粉杠峰值只有 3 个世界单位。
- `catchUpDiffThreshold=3000`，一旦超过就每 1 秒给劣势方补分，把分差压回 3000。
- 结果是阈值后 `currentX` 被锁在约 ±3 附近震荡，**有效净前进距离很小**，很难累积到 0.3 / 0.5 / 1.0。
- 倍率表阈值：0.2→1.1、0.3→1.2、0.5→1.3、1.0→1.5，导致大部分时候只能卡在 1.05。

这不是代码 bug，是**累积速度 × 倍率表 × 阈值上限**三者的数值搭配问题。

### 2.5 其他可能的干扰

- `idleBreathDelay=1` + `breathPeriod=1`：静止 1 秒就起呼吸，与战斗间隙同频，呼吸不断淡入淡出。
- `centerStill` 判定用 `|curX-tgtX|<1e-3 && |curX-lastX|<1e-4`，中线还在 Lerp 尾段极慢移动时就已经被判为静止，呼吸提前启动。

## 3. 修复建议（按优先级）

### 优先级 P0：把呼吸参数拉回合理值

在 `SampleScene.unity` 的 `ShockwavePreview` 组件里改回：

```yaml
breathGapAmplitude: 0.12     # 当前 0.8，建议 0.08~0.15
breathPeriod: 2.4            # 当前 1，建议 2~3
idleBreathDelay: 1.5         # 当前 1，建议 1.5~2，避免太容易起呼吸
```

这是让"大小频繁切"立即消失的最关键一步。

### 优先级 P1：修复衰退中途重新前进"先缩"的 bug

在 `ShockwavePreview.GetAdvanceTarget` 或转换点加保护：

```csharp
private float GetAdvanceTarget(AdvanceState state, float accum, float curScale)
{
    if (state == AdvanceState.Advancing)
    {
        float t = LookupScale(accum);
        // 衰退中重进时，不允许 target 低于当前视觉大小（维持当前大小）
        if (state == AdvanceState.Advancing && _redAdvState == AdvanceState.Advancing) // 需要具体区分
            return Mathf.Max(t, curScale);
        return t;
    }
    return scaleAtRest;
}
```

更简单的实现：**在 `UpdateAdvanceState` 的 `Decay→Advancing` 分支里，把 `accum` 重新校准到对应 `curScale` 的档位下限**，确保 `LookupScale(accum) >= curScale`。

```csharp
// Decay -> Advancing 时
state = AdvanceState.Advancing;
accum += stepFwd;
// 保证重新前进时 target 不低于当前 scale
if (LookupScale(accum) < curScale)
    accum = MinAccumForScale(curScale); // 需要根据倍率表反查最小累积距离
```

### 优先级 P2：削弱或取消 Idle 起跑时的 scale 回缩

把 `forwardAnticipationScaleRatio` 调到 1.0（只弹开、不回缩），或在 `fromDecay=false` 时也允许只弹开。

目前场景里是 0.92，如果保留后弹视觉效果，建议 **只对首次起跑回缩**，或把 ratio 提到 0.98。

### 优先级 P3：放宽"静止"判定，避免呼吸抢戏

在 `Update` 里把 `centerStill` 的阈值放宽：

```csharp
bool centerStill = Mathf.Abs(curX - tgtX) < 5e-3f
                && Mathf.Abs(curX - _lastCenterX) < 1e-3f;
```

让中线真正停下来才开始呼吸。

### 优先级 P4：调倍率表让阈值后变大更明显

当前倍率表：
```csharp
scaleAtRest=1.0, scaleTiny=1.05, scaleAbove0_2=1.1, scaleAbove0_3=1.2, scaleAbove0_5=1.3, scaleAbove1_0=1.5
```

建议改为更敏感的档位（让低累积也能看到明显变粗）：

```csharp
scaleTiny = 1.08f;       // 0 < d < 0.1
scaleAbove0_1 = 1.15f;   // >= 0.1
scaleAbove0_2 = 1.25f;   // >= 0.2
scaleAbove0_4 = 1.35f;   // >= 0.4
scaleAbove0_8 = 1.5f;    // >= 0.8
```

或者把 `pushPerHit` 从 0.001 提高到 0.002 / 0.003（需要同步确认中线移动范围不会穿帮）。

## 4. 最快验证路径（不动代码）

1. 进 Unity，选中 `ShockwavePreview`。
2. 把 `Breath Gap Amplitude` 从 **0.8 → 0.1** 临时改一下，立刻跑 Play。
3. 观察是否"大小频繁切"消失。
4. 若消失，再按 P0/P1/P2/P3 落地。

如果改完呼吸振幅后仍然"切出变大又缩回"，那就是 P1（衰退重进先缩）和 P2（起跑 squeeze）的问题。

## 5. 结论（初版，第 2.4 条已被下方第 6 节推翻）

当前录屏的"大小频繁切"和"推到阈值后不怎么变大"，**不是单一 bug，而是多个叠加效果**：

1. **呼吸振幅被异常放大到 0.8**，把位置开合做成了"大小变化"的视觉假象，是最明显、最优先的问题。
2. **衰退期重新进入前进时 target 可能低于当前 scale**，导致"切出变大又缩回"。
3. **Idle 起跑的 squeeze + 后弹时间过长**，高频起跑时抽搐。
4. **阈值后有效净位移被 catchUp 锁住**，累积爬不上去，本身难变大。（← 见第 6.0 节，此条分析不准确）

建议先按 P0 临时改呼吸参数验证，再按 P1/P2 修复状态机逻辑，最后按 P4 调倍率表。

# 6. 修订后的修复方案（与用户反馈对齐，**未执行**）

## 6.0 先纠正第 2.4 条：不是"缓慢衰减变小"，是被硬切 + 累积被清零

用户实测反馈（推翻初版 2.4）：

> 顶到阈值后并不是断开状态衰减变小，而是**瞬间被切小了，像是被冻结锁住一样**，且持续推进也不会变大，反倒是不推进后一段时间突然切回大的样子。怀疑是残留代码或你做的东西施加了影响。

**这个怀疑是对的。** 我做的三处东西确实在直接影响大小，完整闭环如下：

### 闭环推演

| 阶段 | 发生了什么 | 观感 |
|---|---|---|
| ① 顶到阈值 | `ApplyCatchUp` 每 1s 给劣势方补分 → `targetX` 反向 → `currentX` 反向 → **优势方 `stepFwd = 0`** | 推进被反复打断 |
| ② 进 Decay | 优势方 `timer` 刷不满 → 3s 后转 `Decay` | — |
| ③ **硬切** | `UpdateDecay` 直接 `scale = ScaleFromProgress(p)` 且 **`_redVel = 0f` 清空弹簧速度** → 正在上涨的趋势被一刀切断，从"当前视觉 scale"立刻改为按档位下降 | **"瞬间被切小 / 被冻结锁住"** |
| ④ accum 被清零 | `UpdateDecay` 里 `accum = decayStartAccum * (p / startProgress)` 同步降到接近 0 | — |
| ⑤ 重新推进 | 从极低 accum 重新爬，长期卡在 `LookupScale` 的 1.05 档 | **"持续推进也不会变大"** |
| ⑥ 停止推进 | 中线静止满 1s → 呼吸启动，`breathGapAmplitude=0.8` → 每墙位移 ±0.4 | **"突然切回大的样子"（纯视觉假象）** |

### 三处"我做的东西"在影响大小

| # | 位置 | 问题 | 违反的规则 |
|---|---|---|---|
| A | `ApplyAnticipSqueeze()`（第 299-300 行） | 把 `redTarget/blueTarget` 压到 `curScale × 0.92` —— **回弹直接改了大小** | 位移不得影响大小 |
| B | `UpdateDecay()`（第 585-603 行） | `scale` 由 `ScaleFromProgress(p)` 独立算，与 `accum` 解耦；且 `_redVel=0` 硬切弹簧 | 大小只应由累积距离决定 |
| C | 场景 `breathGapAmplitude: 0.8` | 位移幅度过大，被感知为大小变化 | 循环不得影响大小 |

## 6.1 总原则（用户明确，后续所有改动以此为准）

1. **大小（scale）只由「累积距离 accum」一个参数决定。**
   呼吸循环、回弹位移、闪白、亮度 —— **一律不得影响 scale**。
2. **位移类效果（呼吸开合 / 回弹弹开）只改 `localPosition`，绝不改 `localScale`。**
3. **accum 只在「前进状态」内上升，且只增不减；退出前进状态后（Decay）才开始衰减。**
4. **只有「己方拉开分差所产生的移动」才能累积 accum；扣血补分机制产生的位移除外（不计入、也不给前进状态）。**
5. 大小变化与位移变化**互不影响、互不叠加**，是两条独立通道。

## 6.2 P0 修订：呼吸循环与大小彻底解耦

**现状**：代码层面呼吸确实只走 `ApplyScale` 的 `extra` 位移参数，不改 `localScale`。但场景里振幅被设成 **0.8**（代码默认 0.12），每墙位移 ±0.4 单位，观感上就是"变大/变小"。

**修订要点**：

- `breathGapAmplitude`：`0.8 → 0.12`（验收后可再微调，建议区间 0.06~0.15）
- `breathPeriod`：`1 → 2.4`
- 在 `ApplyScale` 上显式把两条通道分开并固化注释，禁止后续再把 scale 塞进呼吸/回弹路径：

```csharp
// 【通道 1｜大小】只由 accum 决定 -> f，只写 localScale
wall.localScale = new Vector3(baseScale.x * f, baseScale.y * f, baseScale.z * f);
// 【通道 2｜位移】呼吸开合 + 回弹弹开 -> extra，只写 localPosition，绝不影响 f
wall.localPosition = basePos + offset * (1f - f) + extra;
```

- 若 `breathGapAmplitude` 降到 0.12 后仍有"变大"错觉，则改呼吸的表现形式（亮度/纹理脉动），彻底不动位置。

## 6.3 P1 修订：统一「大小 = f(累积距离)」，消除 Decay 的独立 scale 通道

**现状**：`Decay` 里 `scale` 由 `ScaleFromProgress(p)` 独立计算，与 `accum` 是两条曲线（虽然同步下降，但不是同一个函数）。这导致 `target` 与 `curScale` 可能对不上，也是"重进先缩"的来源。

**修订要点**：引入**统一的「档位进度 p」**，让 `accum` 与 `scale` 都成为 p 的函数：

```csharp
// 档位表（倍率 + 对应的累积距离下界）
// p:  0      1        2        3        4        5
// scale: 1.0    1.05     1.1      1.2      1.3      1.5
// accum: 0      0.2      0.3      0.5      1.0      2.0
float AccumFromProgress(float p);   // p -> accum（档间线性）
float ScaleFromProgress(float p);   // p -> scale（档间线性，平滑无硬边）
float ProgressFromAccum(float a);   // accum -> p（AccumFromProgress 的逆）
```

- **Advancing**：`accum += stepFwd`（只增不减）→ `p = ProgressFromAccum(accum)` → `target = ScaleFromProgress(p)`
- **Decay**：`p -= dt / advanceDecayStepTime`（每档 1s）→ `accum = AccumFromProgress(p)`、`scale = ScaleFromProgress(p)` **同步**下降
- 弹簧只负责"平滑追上 target"，**不再被 `_redVel=0` 硬切**（改为进入 Decay 时保留速度、让弹簧自然衔接）

这样"大小"严格是"累积距离"的函数，且衰退时两者仍按档位同步下降（1.5→1.0 仍为 5s，先快后慢不变）。

## 6.4 P2 修订：回弹只做位移，绝不改大小

**现状**（这是用户点名的问题）：

```csharp
ApplyAnticipSqueeze(ref _redAnticipT, ref redTarget, _redScale, _redAnticipFromDecay);
//                                        ^^^^^^^^^ 直接改了目标倍率
```

`forwardAnticipationScaleRatio = 0.92` 会把 target 压到当前倍率的 92%，让墙先缩再冲。

**修订要点**：

- **删除 `ApplyAnticipSqueeze()` 调用与 `forwardAnticipationScaleRatio` 参数**（或把 ratio 恒定为 1.0，保留字段只为不破坏序列化）。
- 回弹只保留 `_redAnticipOff` 位移通道（`forwardAnticipationPullback` 仍可调），**完全不参与 scale 计算**。
- `_redAnticipFromDecay` 标记随之失去意义，可一并清理。

## 6.5 P3 修订：判定改为「双方 1s 内都没有发生移动」

**现状**：

```csharp
bool centerStill = Mathf.Abs(curX - tgtX) < 1e-3f
                && Mathf.Abs(curX - _lastCenterX) < 1e-4f;
```

多了一个 `|curX - tgtX| < 1e-3` 的额外条件，语义是"已追上目标"，不等价于"双方都没移动"。

**修订要点**：改为纯粹看「两侧本帧是否发生移动」：

```csharp
// currentX 对红蓝是共享的：中线不动 == 双方都没移动
bool noMove = Mathf.Abs(curX - _lastCenterX) < 1e-4f;
_idleTimer = noMove ? _idleTimer + dt : 0f;
_lastCenterX = curX;
bool moving = _idleTimer < idleBreathDelay;   // idleBreathDelay = 1.0
```

去掉 `|curX - tgtX|` 条件，严格符合"双方在 1s 内都没有发生移动才起播"。

## 6.6 P4 修订：重新判断「顶到阈值后变大不明显」

### 真正的根因（不是倍率表不匹配）

按 6.0 的闭环，根因是 **两条链**，倍率表只是放大器：

1. **`currentX` 被 catchUp 锁死**：分差被压在 `catchUpDiffThreshold=3000`，`targetX = diff × 0.001` 峰值 ≈ 3.0。`currentX` 收敛到 3.0 附近后就**不再有净前进位移**，`stepFwd` 长期为 0 → `timer` 刷不满 → 必然进 Decay。
2. **Decay 把 accum 清零**：一旦进 Decay，`accum` 被同步降到接近 0，重新推进要从 0 爬，而爬升速率受限于"每周期正向位移"，于是长期停在 1.05。

**所以"调倍率表"只能缓解，不能根治** —— 因为 accum 根本涨不上去，档位再低也会被 Decay 反复清零。

### 三个可选方案（请拍板）

| 方案 | 做法 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **A（推荐）累积来源改「得分事件驱动」** | `ScoreManager.AddScore` 时回调 `shockwave.OnSideScored(side, worldDelta)`，`worldDelta = 分数 × pushPerHit`。Shockwave 用这个量刷新 timer + 累加 accum（按 Lerp 分摊，避免瞬移）。`ApplyCatchUp` 的补分**不回调**。 | 彻底摆脱 `currentX` 共享与 catchUp 污染；严格符合"只有拉开分差产生的移动才能累积"；顶到阈值后只要还在得分就能持续维持并变大 | 需改 `ScoreManager` 加一个回调；需处理"分摊节奏"与视觉同步 |
| **B 放宽维持条件** | 把"每帧位移 > 1e-6"改为"窗口内累计位移 > 阈值"，并延长 `advanceWindowTime`（3s → 5s） | 改动最小，不动 ScoreManager | 治标；`currentX` 收敛后仍无位移可累积，仍会进 Decay |
| **C 纯数值调整** | 倍率表档位下调（如 `0.05/0.1/0.2/0.4/0.8`），或提高 `pushPerHit` | 一行参数 | 缓解不根治；提高 `pushPerHit` 会让 `currentX` 峰值远超 `minX/maxX`（3000×0.003=9）导致穿帮 |

**推荐 A**，理由：它是唯一能同时满足"顶到阈值后仍能维持并变大"和"累积只来自拉开分差"这两个约束的方案，且把"累积"的语义从"共享中线的位移"改为"己方得分产生的位移"，从根上消除 catchUp 与对手得分的干扰。

### 方案 A 的语义确认（需你确认后才会落地）

- `accum` 的输入 = **己方每次得分 × pushPerHit**（世界单位）
- `ApplyCatchUp` 给劣势方的补分 **不产生 accum**（与现有 `ignoreAdvance` 语义一致，只是改由"不回调"实现，`ignoreAdvanceDuration` 可保留作双保险）
- 对手得分导致的 `currentX` 反向 **不影响己方 accum**（本来就只增不减）
- 前进状态的维持 = **有己方得分就刷新 timer**，无得分满 `advanceWindowTime` 才退出
- `currentX` 仍负责"墙的位置"，与"墙的大小"完全解耦

## 6.7 修订后的验收清单

# 8. 二次诊断：A 方案落地后仍「顶到阈值被瞬间切成 1.0 倍」

> 用户反馈（2026-10-07 下午）：A 方案（得分事件驱动累积）落地后，累积与前进状态都正常，
> 但**每次把中线顶出去超过阈值距离，冲击波的视觉大小就被瞬间切掉；被扣血机制弹回后过一段时间又恢复**。
> 用户判断「还有一个机制在强行锁定大小」—— 判断成立，确实有第二个控制者。

## 8.1 真凶：`ShockwaveMeshGenerator.autoFit` 与 `ShockwavePreview` 争夺墙的 Transform

`ShockwavePreview` 并不是墙 Transform 的唯一写入者。`ShockwaveMeshGenerator.Refresh()` 在
`autoFit = true` 时每帧调用 `FitImportedMesh()`：

```csharp
float sx = (frontX - backX) / importedMesh.bounds.size.x;
transform.localScale = new Vector3(sx, sy, sz);
transform.localPosition = targetCenter - localCenterScaled;
```

而 `frontX` 是跟着中缝（`centerLine.currentX`）走的，于是**墙的 X 长度被直接绑定到了中线位置**。

## 8.2 实测数值（决定性证据）

场景里两堵墙当前序列化的 `localScale.x`：

| 墙 | localScale.x | 说明 |
|---|---|---|
| 红墙 | `156.83832` | autoFit 按 `frontX - backX ≈ 5.975`（seam≈0）算出 |
| 蓝墙 | `-156.83832` | 同上，负号=镜像 |

`ShockwavePreview.CaptureBase()` 捕获的 base 也是这个 156.8。反推 mesh `bounds.size.x ≈ 5.975 / 156.8 ≈ 0.038`。

**红墙 `sx = (seam + 5.9) / 0.038`，随中线位置剧烈变化：**

| seam（中线位置） | autoFit 算出的 sx | 相对 base(156.8) |
|---|---|---|
| 0（中心） | ≈ 155 | ≈ 1.0 倍 |
| **-3（被顶到底）** | **≈ 76** | **≈ 0.49 倍（腰斩）** |
| +3（推进到底） | ≈ 234 | ≈ 1.5 倍 |

## 8.3 为什么时好时坏 —— `needWrite` 让两个控制者交替上位

`ShockwavePreview.DriveRuntime()` 只在「本帧视觉确实有变化」时才写墙 Transform：

```csharp
bool needWrite = _breathFade > 1e-3f
    || |scale - lastScale| > 1e-5f
    || anticipOff != 0f;
if (!needWrite) return;   // ← 这一帧放弃控制权
```

- `needWrite = true`（弹簧正在动）→ 写 `base × f`（157 ~ 235）→ **大小正常**
- `needWrite = false`（弹簧已收敛）→ 放弃写入 → **autoFit 的值漏出来**（被推入侧可低至 76）

于是墙在两种完全不同的 scale 之间来回跳，观感就是「瞬间被切成 1.0 倍」。
而「弹回后恢复大小」正是因为 seam 回到 0，autoFit 值回到 ≈155。

✅ 完美吻合用户描述：**累积、前进状态都是好的，只有视觉大小被外部机制锁死。**

两者叠加导致**墙的中缝侧实际移动了 `2 × currentX`**，判定线侧也跟着漂移。
